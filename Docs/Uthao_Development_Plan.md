## 0. What Changed From the Original Proposal

To keep this buildable by four people working apart in about 12–14 hours, we are trimming the proposal:

- **Kafka → RabbitMQ.** Same idea (async events), simpler to run and debug for a student project (one container, one web UI at `localhost:15672`).
- **No WebSocket / real-time location.** Driver location is just a field you update with a normal REST call. No live tracking.
- **No frontend work in this phase.** Phase 1 is backend-only. Every service is tested with Postman. Frontend is a separate phase after merge.
- **No Rating Service for now** (it appears in the architecture diagram but not in the written service list). If time remains after merge, it can be added as a stretch goal — it is the simplest service in the system.

Everything else (7 business services, API Gateway, Eureka registry, Postgres-per-service, JWT auth) stays as proposed.

## 1. Prerequisites (Do This Before the Sprint Starts)

About the database question: the proposal already specifies **PostgreSQL**, not MongoDB — you do not need MongoDB Atlas. Since the team is in four different places and has ~1 day, do **not** set up a shared cloud database either (it adds coordination overhead and a single point of failure). Instead, everyone runs the same `docker-compose.yml` locally — one PostgreSQL container with several databases inside it, plus one RabbitMQ container. This means nobody has to wait on anybody else’s machine or network being up.

Each team member individually installs, before the sprint call:

1. **JDK 21** (Temurin/OpenJDK) — `java -version` should show 21.
2. **Maven** (or use the wrapper `./mvnw` generated by Spring Initializr — no separate install needed).
3. **An IDE** — IntelliJ IDEA (Community is fine) or VS Code + “Extension Pack for Java” + Lombok extension.
4. **Docker Desktop** — needed to run Postgres and RabbitMQ locally with one command.
5. **Postman** (or Insomnia) — for manually testing every endpoint.
6. **Git + a GitHub account.** One teammate creates the repo and adds the other three as collaborators before the kickoff call.
7. **Lombok plugin** enabled in the IDE (IntelliJ: Settings → Plugins → Lombok; also enable annotation processing).

Nothing else is required. No MongoDB, no cloud DB signup, no Kafka install.

## 2. Kickoff Call (30–45 min, all four people, do this first)

This is the only mandatory sync point before everyone splits up. Agree on and write down (into `docs/CONTRACTS.md` in the repo) the following, so nobody needs to interrupt anyone mid-day:

1. **Port numbers** for every service (table below).
2. **Request/response JSON shape** for the handful of objects that cross service boundaries (ride request, driver-assignment result, trip object, payment result).
3. **RabbitMQ exchange/queue/routing-key names** (table below).
4. **JWT format:** shared secret string (just a long random string pasted into `application.yml` on everyone’s machine), token contains `userId` and `role` (`RIDER` or `DRIVER`), header is `Authorization: Bearer <token>`.
5. **Git workflow:** one `main` branch, each person works on their own branch (`feature/identity-gateway`, `feature/rider-eureka`, `feature/driver-matching`, `feature/trip-payment-notification`), open a PR into `main` around hour 10–12, merge one at a time, fix conflicts together on a short call.
6. Everyone pulls the starter repo (with the shared `docker-compose.yml` already in it) and confirms `docker compose up` works on their machine before the call ends.

## 3. Team Assignment

Nine components split four ways. Services that talk to each other the most are paired with the same person, so that person can test that interaction end-to-end without waiting on a teammate.

| Person | Owns | Why paired this way |
|--------|------|---------------------|
| **A** | API Gateway + Identity Service | Gateway needs to validate JWTs issued by Identity — easiest if one person controls both. |
| **B** | Service Registry (Eureka) + Rider Service | Eureka is small boilerplate (a few hours max), leaving room for Rider Service. |
| **C** | Driver Service + Matching Service | Matching Service calls Driver Service constantly (“is this driver free?”); building both together avoids waiting on a contract. |
| **D** | Trip Service + Payment Service + Notification Service | Trip is the central service and calls Payment directly; Notification is intentionally the lightest service (console/DB log only), which balances the extra load. |

If someone finishes early, the stretch task is the optional **Rating Service** (very small: one table, two endpoints — submit rating, get average rating for a user).

## 4. Overall Repository / Folder Structure

One monorepo, one folder per Spring Boot project, so `git clone` gets everything and nobody has to hunt for separate repos.

```text
uthao/
├── docker-compose.yml            # postgres (multi-db) + rabbitmq, shared by everyone
├── docs/
│   └── CONTRACTS.md              # written during kickoff call — DTOs, event names, ports
├── eureka-server/                # Person B
├── api-gateway/                  # Person A
├── identity-service/             # Person A
├── rider-service/                # Person B
├── driver-service/               # Person C
├── matching-service/             # Person C
├── trip-service/                 # Person D
├── payment-service/              # Person D
├── notification-service/         # Person D
└── postman/
    └── Uthao.postman_collection.json   # shared collection, everyone adds their requests
```

### `docker-compose.yml` (conceptually — put this in the repo before the kickoff call)

```yaml
services:
  postgres:
    image: postgres:16
    ports: ["5432:5432"]
    environment:
      POSTGRES_PASSWORD: postgres
    volumes:
      - ./init-db.sql:/docker-entrypoint-initdb.d/init-db.sql
  rabbitmq:
    image: rabbitmq:3-management
    ports: ["5672:5672", "15672:15672"]
```

### `init-db.sql` just creates one database per service

```sql
CREATE DATABASE identity_db;
CREATE DATABASE rider_db;
CREATE DATABASE driver_db;
CREATE DATABASE matching_db;
CREATE DATABASE trip_db;
CREATE DATABASE payment_db;
CREATE DATABASE notification_db;
```

Every service’s `application.yml` points at its own database only (e.g. `jdbc:postgresql://localhost:5432/rider_db`). Nobody’s service touches another service’s tables — that rule stays exactly as in the proposal.

## 5. Communication Contracts (agree at kickoff, then work independently)

### 5.1 Synchronous (REST) calls between services

| Caller → Callee | Purpose |
|-----------------|---------|
| API Gateway → all services | routing |
| Matching Service → Driver Service | check nearby/available drivers |
| Trip Service → Payment Service | start fare calc / payment on trip completion |

Keep it simple: plain `RestTemplate` or `WebClient` calling `http://SERVICE-NAME/...` (resolved via Eureka), or even a hardcoded `localhost:PORT` while developing solo, switched to service-name lookup at integration time. Don’t bother with OpenFeign unless someone already knows it — it’s not worth learning under time pressure.

### 5.2 Asynchronous (RabbitMQ) events

One topic exchange, `uthao.events`. Each consumer creates its own queue bound to the routing key(s) it cares about.

| Routing key | Published by | Consumed by | Payload (minimum fields) |
|-------------|--------------|-------------|--------------------------|
| `driver.assigned` | Matching Service | Trip Service, Notification Service | `tripRequestId`, `riderId`, `driverId`, `driverName`, `eta` |
| `trip.completed` | Trip Service | Payment Service, Notification Service | `tripId`, `riderId`, `driverId`, `distanceKm`, `durationMin` |
| `payment.completed` | Payment Service | Notification Service, Trip Service | `tripId`, `amount`, `status` |
| `trip.cancelled` | Trip Service | Matching Service, Notification Service | `tripId`, `riderId`, `reason` |

Every consumer should just log what it receives and write a row to its own DB — no complex retry or dead-letter handling needed for this project (see [Section 9, Known Limitations](#9-known-limitations-be-upfront-about-these--dont-try-to-hide-them)).

### 5.3 Minimal shared DTOs (put the real JSON in `docs/CONTRACTS.md` at kickoff)

- `RideRequestDto` — `{ riderId, pickupLat, pickupLng, dropLat, dropLng }`
- `DriverAssignmentDto` — `{ tripRequestId, driverId, driverName, vehiclePlate, eta }`
- `TripDto` — `{ tripId, riderId, driverId, status, fare }`
- `PaymentResultDto` — `{ tripId, amount, status }`

### Person A — API Gateway + Identity Service

#### Folder structure

```text
api-gateway/
  src/main/java/com/uthao/gateway/
    GatewayApplication.java
    config/RouteConfig.java
    filter/JwtAuthFilter.java
  src/main/resources/application.yml

identity-service/
  src/main/java/com/uthao/identity/
    IdentityApplication.java
    controller/AuthController.java
    service/AuthService.java
    repository/UserRepository.java
    model/User.java, Role.java
    dto/RegisterRequest.java, LoginRequest.java, AuthResponse.java
    security/JwtUtil.java
  src/main/resources/application.yml
```

#### DB tables (`identity_db`)

`users`, `roles`, `user_roles` (a simple version is fine: a `users` table with a `role` column is enough — skip the join table unless you want the practice).

#### Endpoints

- `POST /auth/register` — create rider or driver, hash password (BCrypt)
- `POST /auth/login` — verify password, return JWT
- (optional) `GET /auth/me` — return decoded user info, useful for debugging

#### Build order

1. Spring Initializr for both projects (Web, Eureka Discovery Client for both; add Spring Cloud Gateway to gateway; add JPA + PostgreSQL + Validation + Lombok to identity-service).
2. Identity Service first: entity → repository → register/login → JWT generation (use `io.jsonwebtoken:jjwt` — small library, easy to use).
3. Test register/login in Postman standalone before touching the gateway.
4. Gateway: add routes for each service (`/api/riders/**` → `rider-service`, etc.), add a simple filter that checks `Authorization` header and rejects if missing/invalid (don’t overbuild role-based route rules — a single “token present and valid” check is enough for a student project).
5. Point the gateway at Eureka once Person B’s registry is up (hour ~9–10); until then, hardcode `lb://identity-service` won’t resolve — just test gateway routing with a direct `localhost:8081` URL during solo dev, switch to `lb://` at integration time.

#### Be careful of

Password hashing (never store plaintext), JWT secret must be the exact string agreed at kickoff (or everyone’s tokens fail validation on other services), gateway CORS config if the team later hooks up a frontend.

### Person B — Service Registry (Eureka) + Rider Service

#### Folder structure

```text
eureka-server/
  src/main/java/com/uthao/eureka/EurekaServerApplication.java
  src/main/resources/application.yml

rider-service/
  src/main/java/com/uthao/rider/
    RiderApplication.java
    controller/RiderController.java
    service/RideRequestService.java
    repository/RiderRepository.java, RideRequestRepository.java
    model/Rider.java, RideRequest.java
    dto/RideRequestDto.java
    event/EventPublisher.java (RabbitMQ)
  src/main/resources/application.yml
```

#### DB tables (`rider_db`)

`riders`, `ride_requests`, `saved_locations` (`saved_locations` is a nice-to-have — skip if short on time).

#### Endpoints

- `POST /riders/requests` — create a ride request (status `REQUESTED`)
- `GET /riders/{id}/trips` — trip history (can just proxy/read from a local cache of trip status updates received via RabbitMQ `trip.completed` / `driver.assigned` — do not call Trip Service synchronously here, keep it simple by storing what you need locally)
- `POST /riders/{id}/requests/{requestId}/cancel` — cancel

#### Build order

1. Eureka Server is genuinely tiny: Spring Initializr with “Eureka Server” dependency, `@EnableEurekaServer`, done in under an hour. Get it running first and leave it running for the rest of the day — everyone else’s `application.yml` should point `eureka.client.service-url.defaultZone: http://localhost:8761/eureka`.
2. Rider Service: entities → repository → create/cancel ride request endpoints.
3. Publish a `ride.requested` event (not in the core table above but useful) so Matching Service can pick it up — agree the exact field names with Person C if you finish early, otherwise a plain REST call from Matching → Rider is an acceptable fallback.
4. Add `@EnableDiscoveryClient` once Eureka is confirmed running.

#### Be careful of

Don’t let Rider Service become a place where you also implement Matching logic — keep matching decisions entirely in Matching Service; Rider Service only owns rider-side data.

### Person C — Driver Service + Matching Service

#### Folder structure

```text
driver-service/
  src/main/java/com/uthao/driver/
    DriverApplication.java
    controller/DriverController.java
    service/DriverService.java
    repository/DriverRepository.java, VehicleRepository.java
    model/Driver.java, Vehicle.java, DriverStatus.java
  src/main/resources/application.yml

matching-service/
  src/main/java/com/uthao/matching/
    MatchingApplication.java
    controller/MatchingController.java
    service/MatchingService.java
    client/DriverServiceClient.java   (RestTemplate/WebClient call)
    repository/MatchRepository.java
    model/MatchRequest.java, MatchHistory.java
    event/EventPublisher.java (RabbitMQ)
  src/main/resources/application.yml
```

#### DB tables

- **`driver_db`:** `drivers`, `vehicles`, `driver_status`, `documents` (`documents` can just be a status enum column instead of a real table — skip file upload entirely)
- **`matching_db`:** `match_requests`, `match_history`

#### Endpoints

- **Driver:** `PATCH /drivers/{id}/status` (online/offline/busy), `GET /drivers/{id}/trips`, `POST /drivers` (register vehicle)
- **Matching:** `POST /matching/find-driver` — takes pickup lat/lng, calls Driver Service for available drivers, picks the nearest one with a simple distance formula (straight-line/Euclidean is fine — no need for the Haversine formula or a mapping API), publishes `driver.assigned`

#### Build order

1. Driver Service first (it’s the dependency): entities → status toggle → “find available drivers near X” endpoint (`GET /drivers/available?lat=&lng=&radiusKm=`). Keep the “nearby” filter dead simple — just compare lat/lng differences against a threshold, don’t build real geospatial queries (PostGIS etc. is overkill here).
2. Test Driver Service alone in Postman: toggle a driver online, hit the “available near” endpoint, confirm it returns.
3. Matching Service: call Driver Service’s “available near” endpoint, pick the first/nearest result, save a `match_history` row, publish `driver.assigned` to RabbitMQ.
4. If no driver is found, matching should still respond (e.g. `NO_DRIVER_FOUND`) rather than hang or 500.

#### Be careful of

“Nearest driver” logic can be as dumb as sorting by distance and taking index 0 — do not attempt a real dispatch/optimization algorithm, it’s explicitly out of scope for a one-day student project.

### Person D — Trip Service + Payment Service + Notification Service

#### Folder structure

```text
trip-service/
  src/main/java/com/uthao/trip/
    TripApplication.java
    controller/TripController.java
    service/TripService.java
    repository/TripRepository.java, TripStatusHistoryRepository.java
    model/Trip.java, TripStatus.java (enum)
    event/EventPublisher.java, EventListener.java (RabbitMQ)
  src/main/resources/application.yml

payment-service/
  src/main/java/com/uthao/payment/
    PaymentApplication.java
    controller/PaymentController.java
    service/PaymentService.java, FareCalculator.java
    repository/PaymentRepository.java
    model/Payment.java
    event/EventPublisher.java
  src/main/resources/application.yml

notification-service/
  src/main/java/com/uthao/notification/
    NotificationApplication.java
    listener/NotificationListener.java (RabbitMQ @RabbitListener)
    repository/NotificationRepository.java
    model/Notification.java
  src/main/resources/application.yml
```

#### DB tables

- **`trip_db`:** `trips`, `trip_status_history`, `trip_routes` (`trip_routes` can just store start/end coordinates — no turn-by-turn routing)
- **`payment_db`:** `payments`, `payment_attempts`, `refunds`, `fare_rules` (`fare_rules` can be a hardcoded constant — e.g. base fare + per-km rate — rather than a configurable table, unless time allows)
- **`notification_db`:** `notifications`, `notification_logs`

#### Endpoints

- **Trip:** `GET /trips/{id}`, `POST /trips/{id}/cancel`, (internal) create-trip triggered by consuming `driver.assigned`
- **Payment:** `POST /payments` — mock payment for a completed trip, always succeeds unless you want to add a fake 10% random-failure for a “handles failure” talking point
- **Notification:** no public endpoints needed beyond `GET /notifications/user/{id}`; everything else happens via `@RabbitListener`

#### Trip status flow (from the proposal, keep exactly this)

`REQUESTED` → `MATCHED` → `ONGOING` → `COMPLETED`, or `NO_DRIVER_FOUND` / `CANCELLED`.

#### Build order

1. Trip Service skeleton first, since it’s the busiest piece: entity, status enum, `@RabbitListener` on `driver.assigned` that creates a trip row in `MATCHED` state.
2. Add `POST /trips/{id}/start` and `POST /trips/{id}/complete` as simple manual-trigger endpoints (in a real app the driver app would call these — for this project it’s fine to trigger them manually via Postman to simulate the driver’s actions, since there’s no real-time tracking).
3. On complete, publish `trip.completed`.
4. Payment Service: `@RabbitListener` on `trip.completed` → calculate a mock fare (flat base + per-km using the distance field from the event, or just a random number if distance isn’t wired through yet) → save payment → publish `payment.completed`.
5. Notification Service last — it’s the simplest, build it once the other two are emitting real events: one `@RabbitListener` method per event, each just inserts a row into `notifications` and prints a log line. This can double as your “proof it all works” demo — watching notification rows appear as you trigger trip/payment actions.

#### Be careful of

This person owns the most moving parts, so build and self-test Trip Service in isolation (using Postman to manually POST a fake “driver assigned” trigger, or a temporary REST endpoint, before RabbitMQ is even wired up) — don’t let Trip Service’s first-ever test run depend on Matching Service being finished.

## 8. Merge & Integration Checklist

1. `docker compose up` (Postgres + RabbitMQ).
2. Start `eureka-server` — confirm dashboard loads at http://localhost:8761.
3. Start all seven business services — confirm each appears registered in the Eureka dashboard.
4. Start `api-gateway` last.
5. Run the shared Postman collection top to bottom: register rider → register driver → driver goes online → rider requests ride → matching assigns driver → trip created → mark trip started → mark trip completed → payment processed → check notifications table has rows for each step.
6. Open the RabbitMQ management UI (`localhost:15672`, default `guest`/`guest`) and confirm messages are flowing through `uthao.events` with no stuck/unacked messages.
7. Merge PRs into `main` one at a time, resolving conflicts on a quick call rather than silently.

## 9. Known Limitations (be upfront about these — don’t try to hide them)

This is intentionally a scoped-down student project. Things left out on purpose, so you can explain them confidently if asked:

- **No saga/rollback pattern.** If Payment fails after a trip is marked completed, there’s no automatic compensating transaction — a real system would need one (e.g., a saga orchestrator), but that’s out of scope here.
- **No real payment gateway** — Payment Service just simulates success/failure.
- **No real-time location tracking** — removed per team decision; driver location is a static field, not a live stream.
- **No geospatial database features** (PostGIS, geohashing) — “nearby driver” uses simple coordinate-distance math.
- **No retry/dead-letter queues on RabbitMQ** — a lost message is just lost; acceptable for a demo, not for production.
- **No automated tests** — verification is manual via Postman. (If time allows, a couple of `@SpringBootTest` smoke tests per service would strengthen the submission.)
- **No containerized deployment of the services themselves** — only Postgres/RabbitMQ run in Docker; the Spring Boot apps run directly from the IDE for the demo. Full containerization (a Dockerfile per service) is a good Phase 2 task.
- **No pagination, no rate limiting, no refresh tokens** — JWTs are simple and don’t expire cleverly; fine for a classroom demo.
